## 1. 用户真正要求的变化

当前交付是 PiDeck 右侧 webview 中的工程产物浏览页面。用户要求的是类似已有 FDTD Workbench 的正式工作台：项目/会话管理、可扩展中央工作区、工程/属性/仿真面板；可以手动修改、运行和看结果，也可以让 Pi 完成同样工作，两种方式随时交接。

本次不是要求放弃网页技术或重写求解器，而是更改产品集成与交互标准。保留 Pi、PiDeck、现有 MCP、CST 后台、案例和全部测试记录；`viewer.py`/独立网页可继续作诊断与证据浏览入口，但不能作为正式工作台完成的替代品。把旧网页放大或嵌入中央 iframe，而没有工程绑定、属性编辑和运行链，也不算满足需求。

长期覆盖 3D、原理图、网格、任务与后处理的主要用户工作流，不以复刻 CST 的每个按钮作为当前前提。用户决定案例和人工验收；开发者自主选择内部小测试、排错和修复，不逐个小测试要求用户审批。

### 2.2 是否继续流程改造

**建议继续工作台集成，但不宣称两例均复现成功。** 偶极子的已有工程链路足以支撑集成开发；先在本机核验原始结果归属和现有运行工件，再作手动/Agent交接回归。222继续保留为必须完成的主案例；当前模型、原理图、配置、失败状态可接入工作台，新完整V/I作为独立未完成项。其资源问题不得阻止所有可做的UI/接口工作，也不得被UI上线掩盖。

本机复核优先检查：任务实际终态、输入模型/参数与结果集对应、复数数组及频率单位/参考阻抗、远场量定义、CAD与实际几何、人工干预与重试。重复性差为0需确认比较的是两次正确归属的数据，不是同一文件或缓存重复读取。此项是要求核查证据，不是断言D3使用了缓存。

## 4. 工作台的用户视图与范围

### 4.1 建议布局

```text
PiDeck / CST Workbench
├─ 左侧：项目、案例、会话、工程文件、历史运行
├─ 聊天区：需求、参数依据、修改、结果解释（可收起）
├─ 中央工作区：3D模型 | 真实网格 | 原理图 | 结果
│  └─ 常用操作：打开/保存、读回刷新、网格、运行选定任务、停止
└─ 右侧工作台：工程身份、选择对象属性、激励/端口、task/求解设置、状态
```

布局是建议，不强迫精确复制CST Ribbon。保留FDTD工作台熟悉的可调分栏、工作区扩展、对象选择、模型/网格分视图及结果入口。工程树负责找到对象和任务，右侧面板负责修改所选项，中央负责观察。

### 4.3 网格与高级视图的可行性门

实际网格仍属于明确目标，不预设所有接口已存在。Codex应查本机对应版本/求解器帮助和实例数据，选定可核验出口。可用结构网格轴/单元、非结构网格节点/连通，或经证明的原生网格截面等表示；记录真实可显示范围，不凭名称套用FDTD的Yee结构。

先交付选定求解器的真实显示，不做全类型平台。若只能取得单元数或原生截图，应明确为统计/截图，不称可交互的实际网格。导出范围有限、隐藏单元或显示抽样须标注；没有接口证据就列未完成，不生成假网格。该缺口不阻止先验收其他工作区功能，但用户未批准缩减目标前，不能宣布整个工作台已全部完成。

两个方向性切面不够还原任意三维辐射图。三维方向图和场动画需真实数据与元数据，作为后续扩展；不通过插值成球面来伪装已取得完整方向图。

## 5. 双入口架构与实现建议

### 5.1 共享的不是聊天，而是工程控制

```text
手动按钮/属性编辑 ─→ PiDeck主进程桥接 ─┐
                                      ├→ 统一CST控制后端 → CST真实工程/求解
Pi自然语言/代码 ─→ 项目级MCP接入 ─────┘           ↓
                                  操作收据、快照、job/run、结果工件
                                      ↓                 ↓
                                 PiDeck工作区       Pi后续查询
```

“统一后端”是一个权威的工程绑定、写锁和作业管理逻辑，不要求只使用一个操作系统进程。已有受监督worker可以保留；禁止UI和Pi各自再创建互不知情的CSTClient/实例、写锁和运行状态。

优先评估已讨论的loopback Streamable HTTP，使桌面主进程与Pi适配器共享同一服务；该标准支持独立服务处理多个客户端，但不等于当前安装组合已兼容 [P1]。若现有单一MCP所有者加桥接更小、更可靠，也可采用并说明。不要两个客户端写同一个stdin，不另造复杂业务平台。沿用现有认证/授权，loopback校验与凭据保护不可省略；渲染层不直接持有CST进程控制权限。

### 5.2 最小状态与动作契约

复用现有类型并补齐至少：`project_id`、`case_id`、`model_revision`、`job_id/run_id`、`artifact_id`。路径是文件定位信息，不代替模型/运行身份。所有用户入口都显式选择当前工程和任务。

修改动作包含目标、预期revision、唯一operation_id、参数/表达式/单位和actor（manual/agent）。成功需读回再发布新快照；错误若已部分修改必须标记并使旧状态失效。UI本地未提交输入显示为草稿，不能让Agent将其当成已生效事实。

作业创建冻结实际输入与配置，完成后结果manifest绑定相同身份及CST结果集/扫参点。旧字段`selected CST farfield`和同路径全目录收集不够；迁移旧工件时无法建立证据关系的保留unknown，不事后猜run_id。

同一工程执行期间修改应被禁止或转到明确的新副本/排队；只读是否允许取决于CST是否可安全响应。切换会话不取消其他运行，也不把别的工程曲线当当前结果。后到快照不得覆盖新revision。

### 5.3 手动运行与停止

保存、参数修改、运行选定task、查看已有结果和停止控制都不需要Provider在线。Agent中断与实际作业中断分开处理；后端持久状态驱动界面。不要从聊天成功/失败文本推断运行终态。

当前已有`terminated/owned_process_tree`恢复方式，不把它改写成“原生暂停/恢复”。按3D与DS分别核对控制路径，按钮标出实际停止方式及工程保护行为。复用同一取消收据，防止UI点停后Agent又重启同一任务。已有取消失败/终止证据保留。

查询/查看结果不得触发求解或破坏历史，尤其保留“No HEX mesh found”相关后处理回归。报告失败优先利用已有结果重生成解释，不因总结失败重新进行物理计算。

### 5.4 文件级落点（提案，须本地核实）

| 位置/组件 | 处理方向 |
|---|---|
| `src/mcp_cst_studio/cst_client.py`、`tools/cases.py` | 复用实际读回/导出/参数与原理图操作，增加稳定身份、明确结果选择和工作区动作 |
| `task_runner.py` | 复用监督、PID身份和取消；补工程revision关联与恢复，不重建调度系统 |
| `server.py`及注册边界 | 桌面和Pi接入同后端，兼容当前工具；证明状态一致与控制可用 |
| `viewer.py`、`web/index.html` | 保留证据浏览入口；提取已有可复用数据解析/显示逻辑，停止把网页功能等同正式UI验收 |
| 独立CST桌面的`features/cst`及主进程/preload桥接 | 新增正式工作区、属性与运行面板；仅是拟议落点，不声称已存在 |
| FDTD参考的`FdtdVisualWorkspace`、`FdtdWorkbenchPanel` | 借鉴分栏、会话绑定、选择和工作台结构；不直接沿用FDTD数据类型/API |
| FDTD参考的模型/网格查看器、结果面板、scoped request gate | 复用有价值的显示与防过期逻辑；CST模型/网格/结果用自己的适配器 |

本次核对FDTD的`FdtdVisualWorkspace.tsx`确认其具有工程/任务/会话作用域、对象选择、独立网格快照和直接桌面API调用 [R6]。这证明有复用入口，不证明CST移植已完成。FDTD仍独立开发，不能修改正在使用的生产工作区。CST桌面源码的仓库/分支、构建和实际启动入口必须在实施说明中明确，不能只提交MCP代码却声称桌面已交付。

## 6. 建议的实施顺序：内部拆分，完整交付

1. **核验当前工件并定位桌面落点。** 先读本机D3原始证据，确认偶极子参考与新运行归属、222当前状态；只核验资料不要求无故重跑全部仿真。列出可以复用的文件、待补契约和实际桌面入口。
2. **接入正式工作区和工程身份。** 工程/会话切换联动，3D/原理图/结果进入中央视图，作业按工程过滤。直接使用已有真实工件验证显示，不能只交空壳。
3. **补手动操作并打通交接。** 从当前案例参数编辑、保存重开、运行/停止、查看结果开始，再验证Pi看到人工新值以及Agent修改后UI刷新。双入口共用控制路径。
4. **完成真实网格与场路设置适配。** 逐类型验证实际网格出口；原理图引脚与负载/探针/任务映射准确。已选案例之外的高级项不抢占主线。
5. **做完整工作台验收并继续222。** 偶极子先完成两入口端到端，222先完成模型/电路/设置/阻塞可见性，资源批准后取得新V/I；其余已选官方例继续作为后续覆盖。

这些是开发顺序，不是要求用户逐步发“继续”。内部测试如何选由Codex安排。遇单项尚无接口先保留证据并推进其他工作；只有需要用户决定的重大差异或预算变化才集中询问。不得用长期接口审计、格式治理或单一小测试代替交付。

## 7. 用户验收与开发者自动检查

### 7.1 用户看到的完整过程

**打开案例 → 切换3D/网格/原理图 → 手动修改参数 → 让Pi读出修改后的实际值 → 手动运行并看结果 → 让Pi再修改/运行 → 工作区同步 → 保存重开仍可继续。**
