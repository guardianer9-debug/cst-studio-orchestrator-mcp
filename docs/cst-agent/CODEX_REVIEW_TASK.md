# Codex：CST Agent R1 方案审查与修订任务

## 任务目标

读取本分支的 CST Agent R0 方案，结合真实源码、本机官方资料、现有 Pi/PiDeck 和历史成果，像软件架构审查一样独立评估并补齐方案，直接更新同一套文档，提交 GitHub 供下一轮复核。

不要仅回复“方案合理”，不要默认 ChatGPT 的建议都正确。指出不必要复杂度、错误假设、缺失需求、已有可复用能力和更合适的替代实现。

## 1. 范围与授权

本轮仅：读取/检索现有文件和版本、分析现有实现与证据、编辑这套文档、进行不执行业务代码的文档结构检查、提交并推送文档工作分支。

不修改生产源码、全局配置、Provider、插件/依赖或 FDTD 工作区；不安装/升级，不启动 CST/MATLAB/FDTD，不连接 CST 做新探测，不运行真实 Pi/Provider 或新仿真实验，不使用 Computer Use。需要实机才能决定的事项写成明确的验证任务和失败退路，不冒充已验。

不提交或推送原有本地业务代码改动。不重置、清理、stash 或覆盖现有工作区以方便拉取。这里的文档提交授权不扩大为功能开发授权。

仓库当前为公开：不上传个人绝对路径、凭据、原始聊天、私有项目片段、完整官方帮助/安装库、受限工程与数据。只提交脱敏事实摘要、公开代码引用和原创设计。

## 3. 必须审查的内容

按顺序阅读 README、architecture-and-delivery-plan.md、capability-matrix.md、review-log.md，并重点回答 Q-01 至 Q-12。

A. 需求是否完整：自然语言/文件输入、必要补问、当前参数与来源、同会话修改、3D/原理图可视化、授权运行、结果、报告和广覆盖目标。核对用户截图所有可见项是否遗漏；没有展开的菜单不猜完整内容。

B. 架构是否最小可行：Pi/PiDeck 复用、CST 与 FDTD 隔离、MCP 与代码不是二选一、同一控制后端、CST 实际工程与 UI 副本关系。指出应该复用、修改、新增的具体文件/模块，不凭空重建 Runtime 或大型通用平台。

C. 现有 MCP 和本地增强：分别标明远端已提交、本地未提交、仅有代码、已有原始运行证据、未验证。尤其审查原理图/RLC/连线/任务、结果读取、所谓异步和弹窗处理。不要再次从零实现已存在能力。

D. 代码执行：Python 与 VBA 的分工、3D/原理图路由、常用封装、通用调用、权限旁路、执行日志和部分失败。不要把 exec、正则过滤、虚拟环境或子进程当成完整沙箱。

E. 运行生命周期：工程绑定/归属、并发写、阻塞求解时的控制通道、查询失败/未知、取消确认、重试幂等、外部修改、保存与依赖恢复、结果新鲜度。不能把普通 API 取消当成 CST 已停止。

F. UI 与数据：3D/CAD/显示面片/仿真网格区别，原理图拓扑与布局区别，对象选择与改名/重建失效，线缆—电路—任务—结果绑定，结果轴/单位/方向/复数与版本。

G. 测试与交付：离线、协议、真实固定脚本、真实 Agent/实际窗口、独立数值五层是否合理；两个最小域案例、负向测试、指标/预算建议；不要把 Mock connected 测试当实机。首包是否过大，哪些检查可以后移但不丢失。

H. 维护与公开边界：当前维护约定与提案冲突、包/运行时兼容、公开许可与资料边界、同文档更新机制。可只读参考已有需求与研究记录，但不恢复暂停的科研或替用户宣称创新。

## 4. 直接交付 R1

2. 更新功能矩阵，优先细化 P0/直接相关 P1：文档来源、版本、已有代码/增强、读写、UI、真实测试状态、最小验收和缺口。未知就写未知，不强行补全 API 名称。
3. 在 review-log.md 追加 R1：总评、阻塞与非阻塞问题、对每项关键建议的同意/修改/反对/待实验、证据和替代方案。
4. 给出建议实施的第一个交付包：最小代码改造点、两个域的小案例、验收项、预算建议和明确停止条件。这里只计划，不执行。
5. 同步 README 的版本、状态和下一动作；本任务文件仅在流程错误时修订，不将未来实施任务混入当前授权。

只在真正阻塞的需求/权限冲突时集中提问；其他不确定性写明并继续完成其余审查。
